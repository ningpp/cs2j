## linq-channel 预处理 pass 性能优化（2 文件，输出逐字节不变）

**背景**：`convert-project` 没有 `-p/--pass` 选项（只有 `preprocess` 动词有），用户给的
`convert-project ... --pass linq-channel` 会解析失败并**静默返回 1**（不打印任何错误）。
等价命令：
`dotnet ... dll preprocess -s <src> -d <dst> --no-verify-build --no-verify-tests --pass linq-channel`

**基准输入**：`D:\cs\cs-sdk-349fe3f4`（1277 个 .cs，已 member-desugar、未 linq-channel；
其 `.cs2j-member-desugar-src` 已被上次 promote 清理掉，故直接复制该树当输入）。
1277 个文件里只有 465 个触发 stage-2（`MayBeRewritten`），本树上 `rewrittenChainCount=0`
（全是 uncoveredOperators / skipped），即纯空跑 90s+。

**剖析结论（临时插桩，已移除）**：
- `LinqRewriter.Visit` 占 ProcessFile 的 95%（88.8s/930 次调用），plan 3.4s、gate 0.9s、
  desugar2 0.3s、IsEquivalentTo≈0。
- 每文件被 `ProcessFile` 调用 **2 次**：stage-2 真跑 + §7.10 residual 幂等复检，
  各占约 48% / 36%。
- 4 次 `BuildIntermediateCompilation`（stage2 / residual / closure-lift / iterator-lowering），
  每次全树重解析 ~1.3~2.3s。
- 原实现每文件在 `compilation.SyntaxTrees` 上做 `FirstOrDefault` 线性查找 → O(N²)。

**改动**：
1. `LinqChannelPassAdapter`：stage-2 与 residual 两个 per-file 循环改为
   `Parallel.For` 计算 + 顺序合并（statistics/diagnostics/写盘/processedInputs 均按文件序），
   新增 `IndexSyntaxTreesByPath`（路径→SyntaxTree 字典）与 `RethrowFirstFailure`
   （用 ExceptionDispatchInfo 还原首个异常，避免 AggregateException 改变失败形态）。
2. `BuildIntermediateCompilation` 的读+解析改为并行，树序仍按 `pairs`。
3. `LinqChannelRewriter.ProcessFile`：`RewriteChanged` 先做 `ReferenceEquals` 短路；
   residual 的 `ToFullString()` 文本比较同样先 `ReferenceEquals` 短路。

**验证**：
- 输出全量清单（1627 个文件，含 obj/ 与 `cs2j-linq-channel-report.json`）与基线
  **逐字节一致**，树 md5 均为 `4badf85f4756fe0d81c84be0271aa45c`。
- 同一二进制交替 A/B：串行 108.57s / 88.89s，并行 56.75s / 51.86s；
  最终版单跑 49.4~53.5s（prepare 不计），约 **1.8x**。
- 测试：`CSharpToJava.Tests` LinqChannel 209 项全过；
  `CSharpToJava.ProjectTests` 12 过 / 3 跳过 / 1 失败
  （`RestoredPackageReferences_BindMetadataOnlySymbols_NoFalseLc0010`，
  基线同样失败，属既有问题，与本次改动无关）。
